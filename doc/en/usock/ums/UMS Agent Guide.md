# UMS Agent Guide
This document is intended for system administrators and deployment engineers. It introduces the positioning, architecture, installation, configuration, certificate management, service operations, and troubleshooting of the UMS security agent ums_agent. For basic concepts of UMS and Token modes, see [UMS User Guide](./UMS%20User%20Guide.md). For socket programming interfaces, see [UMS API Guide](./UMS%20API%20Guide.md).

## 1. Overview
### 1.1 Positioning
ums_agent is the **userspace security agent** of UMS, running as a systemd service. In SECURE Token mode (`ub_token_mode=0`), ums_agent exchanges UB TokenValue out-of-band between cross-node UMS kernel modules over a TLS 1.3 encrypted channel, eliminating the risk of plaintext Token transmission over the control plane. ums_agent is only responsible for the secure transmission of TokenValue; it does not participate in Token generation (TokenValue is generated by the kernel) and does not persistently store TokenValue (cleared immediately after transmission and delivery).

In LEGACY and DISABLE modes, the kernel does not use ums_agent. ums_agent is allowed to start in these two modes (for pre-deployment convenience), but the kernel will not submit Tokens to it.

### 1.2 Core Capabilities
- Cross-node encrypted channel establishment and maintenance based on OpenSSL TLS 1.3 (connection pool, on-demand connection)
- X.509 certificate mutual authentication
- Netlink communication with the UMS kernel module
- Secure negotiation, delivery, and clearing of TokenValue
- Runs as a systemd `Type=notify` service with automatic restart on failure
- Runs with minimal privileges as the dedicated system user `ums` (only `CAP_NET_ADMIN`)

### 1.3 Applicable Scenarios
- Production environments where security compliance requires TokenValue encrypted transmission
- Applications without TLS enabled at the application layer, where TokenValue leakage prevention is needed to protect the data plane
- Applications with TLS already enabled at the application layer, where defense in depth for control plane credential transmission is still needed

For mode selection and cost trade-offs, see [UMS User Guide - 5. Token Mode and Security](./UMS%20User%20Guide.md#5-token-mode-and-security).

## 2. Token Exchange Process
In SECURE mode, a single UMS connection establishment involves four channels:

| Channel | Payload | Description |
| ------- | ------- | ----------- |
| TCP clcsock (control plane) | CLC handshake Proposal/Accept/Confirm | In SECURE mode, the Token field is filled with 0 as a placeholder |
| TLS 1.3 channel (out-of-band) | TokenValue | Between ums_agent instances, default port 61080 |
| Netlink (intra-node) | TOKEN_SUBMIT / TOKEN_DELIVER | UMS kernel ↔ local ums_agent |
| UB network (data plane) | Application data | Transmitted via URMA Jetty/SEG after connection establishment |

In SECURE mode, during the CLC handshake (Proposal → Accept → Confirm), the Token field is filled with 0 as a placeholder. Both parties' TokenValues are exchanged out-of-band via the ums_agent TLS 1.3 channel. After the application calls `connect()` to trigger the CLC Proposal, the TokenValue in each direction is generated by the local kernel and delivered to the peer kernel along the following path:

Local kernel generates TokenValue → `TOKEN_SUBMIT` (Netlink) → local ums_agent → TLS 1.3 channel → peer ums_agent → `TOKEN_DELIVER` (Netlink) → peer kernel stores

The reverse flow works the same way. TokenValue exchange proceeds in parallel with the CLC Accept/Confirm: the CLC negotiation handshake can only complete after both kernels have obtained the peer's TokenValue, and the UMS data plane URMA channel is successfully established.

## 3. Prerequisites
### 3.1 System Requirements
| Requirement | Description |
| ----------- | ----------- |
| Operating system | openEuler (kernel version ≥ 6.6) |
| UMS kernel module | `ums.ko` installed and loaded, with `ub_token_mode=0` (SECURE) |
| UB hardware | UB network devices deployed, URMA component installed and configured |
| Network connectivity | TCP reachable between all nodes (ums_agent default listen port 61080) |
| System user | The `umdk-ums-agent` package automatically creates the system user `ums` upon installation |

### 3.2 PKI Certificate System
SECURE mode requires deploying an X.509 certificate system. All nodes must use certificates issued by the same CA. ums_agent acts as both TLS server and client, requiring separate server and client certificate configuration.

| Certificate/File | Purpose | Requirements |
| ----------------- | ------- | ------------ |
| CA certificate (ca.crt) | Verify peer certificate chain | Consistent across all nodes |
| Server certificate (server.crt) | TLS server identity authentication | SAN extension containing the local node IP is recommended |
| Server private key (server.key) | Private key for the server certificate | Must be stored encrypted (PEM format), passphrase loaded into Keyring |
| Client certificate (client.crt) | TLS client identity authentication | Issued by the same CA |
| Client private key (client.key) | Private key for the client certificate | Must be stored encrypted (PEM format), passphrase loaded into Keyring |
| CRL (crl.pem, optional) | Certificate revocation list | Loaded at startup, updates require restarting ums_agent |

### 3.3 ums System User
ums_agent runs as the dedicated system user `ums`. It is automatically created via the `%pre` script during RPM installation:
```
Username: ums
Type:     system user (-r)
Shell:    /sbin/nologin
Home:     /var/lib/ums
```
To create manually:
```bash
sudo useradd -r -s /sbin/nologin -d /var/lib/ums ums
```

### 3.4 Private Key Passphrase and Linux Keyring
ums_agent reads the private key decryption passphrase from the Linux Keyring (`@u` user keyring) at startup. The passphrase must be loaded before ums_agent starts. The systemd service is configured with `KeyringMode=shared` to ensure the service can access the `ums` user's Keyring.

```bash
# Method 1: Manual injection
# Load the private key passphrase into the Keyring (@u) as the ums user
# <desc> is the value of prkey_pwd_desc in the config file, <passphrase> is the private key decryption passphrase
# Note: The following command is only for dev/test environments. Production environments should use
#       a security-compliant method to load the passphrase, avoiding exposing plaintext on the command line
sudo -u ums keyctl add user <desc> <passphrase> @u

# Method 2: Automatic passphrase injection via systemd pre-start stage (ExecStartPre)
# Automatic passphrase injection via the systemd pre-start stage
# Configure a script to run in the ExecStartPre stage in the [Service] section of the ums_agent.service file
# Example: ExecStartPre=/etc/ums_agent/ums_prkey_pwd_init.sh

# View the passphrase injection result
sudo -u ums keyctl list @u
```

## 4. Installation
### 4.1 RPM Package Information
ums_agent is installed via the `umdk-ums-agent` subpackage, which is part of the UMDK RPM.

| Attribute | Value |
| --------- | ----- |
| Subpackage name | `umdk-ums-agent` |
| Summary | UMS Agent daemon for secure token exchange |
| Runtime dependencies | `systemd-libs`, `glib2`, `libnl3`, `openssl`, `keyutils` |
| Pre-install dependency | `shadow-utils` (creates the ums system user) |
| Build dependencies | `systemd-devel`, `keyutils-libs-devel`, `openssl-devel` |

### 4.2 Installed File Listing
| File Path | Permission | Owner | Description |
| --------- | ---------- | ----- | ----------- |
| `/usr/sbin/ums_agent` | 750 | root:ums | ums_agent executable |
| `/usr/lib/systemd/system/ums_agent.service` | 644 | root:root | systemd service unit |
| `/etc/ums_agent/` | 750 | root:ums | Configuration directory |
| `/etc/ums_agent/ums_agent.conf` | 640 | root:ums | Main configuration file (`config(noreplace)`, not overwritten on upgrade) |
| `/etc/rsyslog.d/ums_agent.conf` | 644 | root:root | rsyslog logging configuration |
| `/etc/logrotate.d/ums_agent` | 644 | root:root | Log rotation configuration |

Note: Certificate files (`/etc/ums_agent/certs/`) are not provided by ums_agent; the administrator must generate and deploy them (see [6. Certificate and Key Management](#6-certificate-and-key-management)).

### 4.3 Installation and Uninstallation
**Installation**:
```bash
sudo rpm -ivh umdk-ums-agent-*.rpm
```
Installation automatically executes: create the `ums` system user (`%pre`) → restart rsyslog (`%post`) → enable `ums_agent.service` via systemd macros (does not auto-start).

**Verify installation**:
```bash
ls -la /usr/sbin/ums_agent
systemctl cat ums_agent.service
ls -la /etc/ums_agent/
id ums
```

**Uninstall**:
```bash
sudo rpm -e umdk-ums-agent
```
Before uninstalling, `ums_agent.service` is automatically stopped and disabled.

## 5. Configuration
### 5.1 ums_agent.conf
Configuration file path: `/etc/ums_agent/ums_agent.conf`, permission 640, owner root:ums. Restart the service after modification for changes to take effect:
```bash
sudo systemctl restart ums_agent
```

**Configuration Reference**:

| Section | Option | Required | Default | Description |
| ------- | ------ | -------- | ------- | ----------- |
| `[logging]` | `log_level` | No | `info` | Log level: emerg/alert/crit/err/warning/notice/info/debug |
| `[authenticate.client]` | `x509.truststore` | Yes | — | CA certificate path, verifies peer certificate chain, must be consistent across all nodes |
| `[authenticate.client]` | `x509.certificate` | Yes | — | Client certificate path |
| `[authenticate.client]` | `x509.private_key` | Yes | — | Client private key path, must be stored encrypted, passphrase loaded into Keyring (`@u`) |
| `[authenticate.client]` | `x509.prkey_pwd_desc` | Yes | — | Descriptor of the client private key passphrase in Keyring (`@u`), length < 128 characters |
| `[authenticate.client]` | `x509.crl` | No | empty | Client-side CRL path |
| `[authenticate.server]` | `x509.truststore` | Yes | — | CA certificate path, same as above |
| `[authenticate.server]` | `x509.certificate` | Yes | — | Server certificate path |
| `[authenticate.server]` | `x509.private_key` | Yes | — | Server private key path, must be stored encrypted |
| `[authenticate.server]` | `x509.prkey_pwd_desc` | Yes | — | Descriptor of the server private key passphrase in Keyring (`@u`) |
| `[authenticate.server]` | `x509.crl` | No | empty | Server-side CRL path |
| `[network]` | `listen_port` | No | `61080` | TLS listen port, range 1024–65535 |
| `[network]` | `listen_addr` | Yes | — | TLS listen address, must be consistent with the local IP used for establishing UMS socket connections; supports IPv4/IPv6, does not support hostnames |
| `[network]` | `max_conns` | No | `1024` | Maximum concurrent TLS connections (connection pool size), range 1–65535 |
| `[tls]` | `cipher_suite` | No | `TLS_AES_256_GCM_SHA384` | TLS 1.3 cipher suite, currently only this suite is supported |

**Configuration Example (SECURE mode production environment)**:
```ini
[logging]
# log_level optional value: emerg, alert, crit, err, warning, notice, info, debug
log_level=info

# Authenticate x509 Options
# -------------------------------------------------------------------------------
# x509.truststore    : (REQUIRED) Path to trusted CA certificate store (verify peer certificate)
# x509.crl           : Path to Certificate Revocation List (optional, can be empty)
# x509.certificate   : (REQUIRED) Path to local certificate (present identity to peer)
# x509.private_key   : (REQUIRED) Path to local private key (for TLS signing, private key file should be encrypted)
# x509.prkey_pwd_desc: (REQUIRED) Private key decryption password from Keyring (@u)
#                      IMPORTANT: Password must be stored in Keyring (@u) before service starts
#                                 Methods: 1) keyctl manually, 2) ExecStartPre in ums_agent.service
# -------------------------------------------------------------------------------

[authenticate.client]
x509.truststore=/etc/ums_agent/certs/ca.crt
# x509.crl=/etc/ums_agent/certs/crl.pem
x509.certificate=/etc/ums_agent/certs/client.crt
x509.private_key=/etc/ums_agent/certs/client.key
x509.prkey_pwd_desc=client_private_key_passphrase

[authenticate.server]
x509.truststore=/etc/ums_agent/certs/ca.crt
# x509.crl=/etc/ums_agent/certs/crl.pem
x509.certificate=/etc/ums_agent/certs/server.crt
x509.private_key=/etc/ums_agent/certs/server.key
x509.prkey_pwd_desc=server_private_key_passphrase

[network]
# listen_port: TCP/TLS listen port for inter-node ums_agent communication
listen_port=61080
# listen_addr: (REQUIRED) TCP/TLS listen address, must be consistent with the local IP address
#              used for establishing UMS socket connection
#              Format: IPv4 (e.g., 192.0.2.10) or IPv6 (e.g., 2001:db8::1)
#              Hostname is NOT supported
listen_addr=192.0.2.10

# max_conns: Maximum concurrent TCP/TLS connections (connection pool size), valid range: 1-65535
max_conns=1024

[tls]
# cipher_suite: TLS 1.3 cipher suite for secure channel
# Supported: TLS_AES_256_GCM_SHA384
cipher_suite=TLS_AES_256_GCM_SHA384
```

**Configuration Key Points**:
1. `listen_addr` must be consistent with the local IP used for establishing UMS socket connections on that node, otherwise the peer ums_agent cannot connect back.
2. ums_agent acts as both TLS server and client; client and server certificates must be configured separately.
3. Private keys must be stored in encrypted form (PEM); at startup, the passphrase is queried from the Keyring for decryption.
4. `prkey_pwd_desc` must match the descriptor used when loading the passphrase into the Keyring.
5. CRL is only loaded at startup; updating the CRL requires restarting ums_agent.

### 5.2 Kernel Module Parameters
SECURE mode requires the UMS kernel module to be loaded with `ub_token_mode=0`. For complete parameter descriptions and configuration examples, see [UMS User Guide - 3.4 Kernel Module Parameter Configuration](./UMS%20User%20Guide.md#34-kernel-module-parameter-configuration). This section only describes the `ums_agent_uid`/`ums_agent_gid` configuration mechanism directly related to ums_agent.

`ums_agent_uid` / `ums_agent_gid` default to 0 (only root can register). In production environments, it is recommended that systemd `ExecStartPre` automatically writes the `ums` system user's UID/GID before ums_agent starts (default behavior, see [5.3 systemd Service](#53-systemd-service)), allowing ums_agent to run with minimal privileges.

To use the `ums` user identity for verification at module load time (without relying on `ExecStartPre`), pre-configure via `/etc/modprobe.d/ums.conf`:
```bash
# /etc/modprobe.d/ums.conf
options ums ub_token_mode=0 ums_agent_uid=<ums_user_UID> ums_agent_gid=<ums_user_GID>
```

Note: `ums_agent_uid`/`ums_agent_gid` cannot be modified while the agent is online; modifications must be done while the agent is offline.

### 5.3 systemd Service
Default service unit: `/usr/lib/systemd/system/ums_agent.service`. To customize, create `/etc/systemd/system/ums_agent.service` as an override, and run `systemctl daemon-reload` after modification.

**Default service unit key configuration**:
```ini
[Unit]
Description=Security Agent for kernel UMS module
After=network.target
Documentation=man:ums_agent(8)

StartLimitIntervalSec=60s
StartLimitBurst=5

[Service]
Type=notify
User=ums
Group=ums
KeyringMode=shared

ExecStartPre=+/bin/sh -c 'id -u ums > /sys/module/ums/parameters/ums_agent_uid'
ExecStartPre=+/bin/sh -c 'id -g ums > /sys/module/ums/parameters/ums_agent_gid'
ExecStart=/usr/sbin/ums_agent --config /etc/ums_agent/ums_agent.conf
ExecStopPost=+/bin/sh -c 'echo 0 > /sys/module/ums/parameters/ums_agent_uid'
ExecStopPost=+/bin/sh -c 'echo 0 > /sys/module/ums/parameters/ums_agent_gid'

CapabilityBoundingSet=CAP_NET_ADMIN
AmbientCapabilities=CAP_NET_ADMIN
NoNewPrivileges=yes

Restart=on-failure
RestartSec=3s

KillSignal=SIGTERM
TimeoutStopSec=10s

[Install]
WantedBy=multi-user.target
```

| Option | Description |
| ------ | ----------- |
| `KeyringMode=shared` | **Required**, enables ums_agent to access the `ums` user's Keyring (`@u`) to read the private key passphrase |
| `ExecStartPre` | Writes `ums_agent_uid`/`ums_agent_gid` to the `ums` user's UID/GID, allowing the agent to register with minimal privileges |
| `ExecStopPost` | Resets `ums_agent_uid`/`ums_agent_gid` to 0 after service stops (restores root-only) |
| `CapabilityBoundingSet=CAP_NET_ADMIN` | Grants only the minimal capability needed for Netlink communication |
| `NoNewPrivileges=yes` | Prevents child processes from gaining additional privileges |

**Command-line Options**:
```bash
ums_agent --config <path>   # Specify the configuration file, path must be under /etc/ums_agent/
ums_agent --version         # Show version
ums_agent --help            # Show help
```

## 6. Certificate and Key Management
### 6.1 Certificate Directory and Permissions
```bash
sudo mkdir -p /etc/ums_agent/certs
sudo chown root:ums /etc/ums_agent/certs
sudo chmod 750 /etc/ums_agent/certs

# Certificate files
sudo chmod 644 /etc/ums_agent/certs/ca.crt
sudo chmod 644 /etc/ums_agent/certs/server.crt /etc/ums_agent/certs/client.crt
sudo chmod 640 /etc/ums_agent/certs/server.key /etc/ums_agent/certs/client.key
sudo chown root:ums /etc/ums_agent/certs/server.key /etc/ums_agent/certs/client.key
```

### 6.2 Certificate Generation Example (Dev/Test Environment)
The following steps are only applicable to dev/test environments. Production environments should use the organization's internal PKI system to issue certificates.

```bash
# Generate a self-signed CA root certificate and the corresponding RSA private key
openssl req -newkey rsa:2048 -passout pass:123456 -keyout ca_rsa_private.pem -x509 -days 365 -out ca.crt -subj "/C=CN/ST=Beijing/O=UMS-Test/CN=UMS Test CA"

# Generate an RSA private key file (encrypted) and a certificate signing request (CSR) file for the server
openssl req -newkey rsa:2048 -passout pass:srv123 -keyout server_rsa_private.pem -out server.csr -subj "/C=CN/ST=Beijing/O=UMS-Test/CN=ums-server"

# Use the CA root certificate and private key to sign the server certificate
openssl x509 -req -days 365 -in server.csr -CA ca.crt -CAkey ca_rsa_private.pem -passin pass:123456 -CAcreateserial -out server.crt

# Generate an RSA private key file (encrypted) and a certificate signing request (CSR) file for the client
openssl req -newkey rsa:2048 -passout pass:clnt123 -keyout client_rsa_private.pem -out client.csr -subj "/C=CN/ST=Beijing/O=UMS-Test/CN=ums-client"

# Use the CA root certificate and private key to sign the client certificate
openssl x509 -req -days 365 -in client.csr -CA ca.crt -CAkey ca_rsa_private.pem -passin pass:123456 -CAcreateserial -out client.crt

# 5. Deploy
sudo cp ca.crt server.crt client.crt /etc/ums_agent/certs/
sudo cp server_encrypted.key /etc/ums_agent/certs/server.key
sudo cp client_encrypted.key /etc/ums_agent/certs/client.key

# Set directory and file permissions per §6.1
```

### 6.3 Certificate Update
1. Apply for a new certificate (re-issue with the existing CA, or use a new CA).
2. Replace the certificate and private key files.
3. Reload the private key passphrase into the Keyring (`@u`).
4. Restart ums_agent:
   ```bash
   sudo systemctl restart ums_agent
   ```
When changing the CA, ensure all nodes are updated synchronously, otherwise mutual authentication will fail.

### 6.4 Certificate Revocation Example
1. Generate CRL: `openssl ca -gencrl -out crl.pem -config openssl.cnf`
2. Deploy: `sudo cp crl.pem /etc/ums_agent/certs/crl.pem`
3. Configure the `x509.crl` path in the `[authenticate.client]` and `[authenticate.server]` sections of `ums_agent.conf`.
4. Restart ums_agent.

CRL is only loaded at startup; updating the CRL requires restarting ums_agent.

## 7. Service Management
### 7.1 Pre-startup Checks
Before the first start, ensure:
1. The `umdk-ums-agent` package is installed
2. Certificates are deployed to `/etc/ums_agent/certs/`
3. `/etc/ums_agent/ums_agent.conf` is properly configured (especially `listen_addr`)
4. The private key passphrase is loaded into the Keyring (`@u`)
5. The UMS kernel module is loaded with `ub_token_mode=0`

### 7.2 Common Commands
```bash
sudo systemctl start ums_agent      # Start
sudo systemctl stop ums_agent       # Stop (after stopping, the kernel sets available to 0, subsequent CLC handshakes Decline due to inability to submit Token)
sudo systemctl restart ums_agent    # Restart
sudo systemctl status ums_agent     # Check status
sudo systemctl enable ums_agent     # Enable auto-start on boot
sudo systemctl disable ums_agent    # Disable auto-start on boot
```

### 7.3 Logs
ums_agent logs are output via rsyslog to `/var/log/umdk/ums/ums_agent/ums_agent.log`, in the format:
```
RFC3339_timestamp|severity|process_name[PID]|message
```

```bash
# Tail the log file in real time
sudo tail -f /var/log/umdk/ums/ums_agent/ums_agent.log
# Follow service logs in real time via journalctl
sudo journalctl -u ums_agent -f
# Search service logs by time range
sudo journalctl -u ums_agent --since "2026-05-28 10:00:00" --until "2026-05-28 11:00:00"
```

Log rotation is managed by logrotate: maximum retention 365 days, 30 rotations, auto-rotate when exceeding 1024k, compressed storage. The default configuration file is `/etc/logrotate.d/ums_agent`, which can be modified as needed.

## 8. Mode Interoperability
### 8.1 Interoperability Matrix
| Local Mode \ Peer Mode | SECURE(0) | LEGACY(1) | DISABLE(2) |
| ---------------------- | --------- | --------- | ---------- |
| SECURE(0) | Interoperable | Not interoperable (`UMS_CLC_DECL_TOKMDMIS` (0x09990006), fall back to TCP) | Not interoperable (fall back to TCP) |
| LEGACY(1) | Not interoperable (fall back to TCP) | Interoperable | Interoperable |
| DISABLE(2) | Not interoperable (fall back to TCP) | Interoperable | Interoperable |

Rule: SECURE only interoperates with SECURE; LEGACY and DISABLE interoperate with each other. All nodes must be uniformly configured with the same mode.

## 9. Troubleshooting
### 9.1 Common Issues
| Symptom | Possible Cause | Troubleshooting Suggestions |
| ------- | -------------- | --------------------------- |
| `systemctl status ums_agent` shows startup failure | Configuration file missing or required fields not filled | Check `/etc/ums_agent/ums_agent.conf`, confirm `listen_addr` and certificate/private key file paths are configured |
| Log reports private key passphrase read failure | Passphrase not loaded in Keyring, or `prkey_pwd_desc` mismatch | Run `keyctl list @u` as the `ums` user to confirm passphrase is loaded; verify descriptor matches configuration |
| TLS handshake failure | Certificates not issued by the same CA, or certificate expired | Confirm `ca.crt` is consistent across all nodes; check validity with `openssl x509 -in <cert> -noout -dates` |
| UMS kernel CLC handshake error `UMS_CLC_DECL_TOKMDMIS` (0x09990006) | `ub_token_mode` inconsistent across nodes | Check `dmesg \| grep "UMS_" \| grep "ub_token_mode="` on all nodes, unify to SECURE(0) |
| ums_agent is online but UMS connection still Declines | ums_agent not successfully registered with the kernel | Check kernel logs `dmesg \| grep ums`, confirm agent available; confirm `ums_agent_uid/gid` matches the running user |
| `ums_agent_uid` modification returns `-EBUSY` | Modification not allowed while agent is online | First `systemctl stop ums_agent`, then modify, then start |

### 9.2 Diagnostic Commands
```bash
# Kernel side: check token mode (ub_token_mode permission is 0, can only be confirmed from load logs, UMS log prefix is [UMS_)
dmesg | grep "UMS_" | grep "ub_token_mode="
# Check agent identity parameters (0644, readable and writable)
cat /sys/module/ums/parameters/ums_agent_uid
cat /sys/module/ums/parameters/ums_agent_gid
# Check agent registration and token-related kernel logs
dmesg | grep "UMS_"

# Agent side: service status and logs
systemctl status ums_agent
sudo tail -100 /var/log/umdk/ums/ums_agent/ums_agent.log

# Connection status
cat /proc/net/ums
```
